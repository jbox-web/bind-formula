# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Context

This is the `jbox-web` fork of `saltstack-formulas/bind-formula`. The parent
directory's `CLAUDE.md` covers the fork collection, the shared toolchain and
the CI; this file only records what is specific to this formula.

In production the entry point is `bind.config` (which includes `bind`), on a
zone master and a slave. `AUDIT.md` (untracked, 2026-10-17) lists the pillar
keys set in production and the hosts; some of its findings were fixed afterwards in
`fc59ce6` (`/etc/default/named`, `bind9-utils`, `named-checkconf`).

## Commands

```bash
bundle install
bin/install-hooks                               # pre-commit + commit-msg hooks

bin/kitchen list                                # 3 instances: default-<platform>
bin/kitchen test default-debian-13-3008-2       # one instance, end to end
pre-commit run --all-files                      # yamllint, salt-lint, rubocop, ...
```

One Kitchen suite, `default`: `state_top` is `bind._mapdata`, `bind`,
`bind.config`; its pillar is `test/salt/pillar/default.sls` (not
`pillar.example`). Nothing tests views (`pillar-with-views.example`), DNSSEC,
`rndc_client`, extensive logging, forward zones or `bind.utils`.

## Architecture — this formula predates the template layout

Do not apply the parent `CLAUDE.md`'s "Architecture of a formula" section here:

- **Three flat states.** `init.sls` installs the packages, runs the service
  (`reload: True`) and creates the key directory. `config.sls` does everything
  else. `utils.sls` only installs `bind9-host` and is included by nothing.
- **No `tplroot`.** States import `"bind/map.jinja"` literally; only
  `_mapdata/init.sls` derives `tplroot`.
- **Inline `map.jinja`, no YAML maps.** One `grains.filter_by` by `os_family`,
  merged with an empty `oscodename` level, an `os` level (Ubuntu only), then
  `bind:lookup`. No `defaults.yaml`, no `libtofs.jinja`.
- **Two pillar namespaces.** `bind:lookup` is merged into `map`;
  `bind:config:*` (`user`, `group`, `mode`, `log_mode`, `tmpl`, `protocol`,
  `options`, `includes`, `default_zones`, `use_extensive_logging`, …) is read
  ad hoc with `pillar.get('bind:config:<key>', map.<key>)` in each state and
  template. A key set under the wrong namespace is silently ignored.
  `init.sls` reads `bind:config:key_directory`, `config.sls` reads
  `bind:lookup:key_directory`.
- **No TOFS.** Sources are `salt://{{ map.config_source_dir }}/<file>`, one
  directory per OS family under `bind/files/`, plus the shared
  `named.conf.local.jinja`, `named.conf.logging.jinja` and `zone.jinja`.
  `bind:config:tmpl` replaces `named.conf` only. Any other override shadows the
  `salt://bind/files/...` path in the master's file roots.
- **Debian-only files.** `named.conf.key`, `.options`, `.default-zones`,
  logrotate and `rndc.conf` are under `if grains['os_family'] == 'Debian'`.

### Reload, restart, check

- Two `service.running` states on the same unit: `bind` (from `init.sls`,
  reload) receives `watch_in` from the config and zone files; `bind_restart`
  (`reload: False`) watches `query.log`, the key directory and
  `bind_default_config` (`/etc/default/named` on Debian, where `protocol`
  becomes `-4`/`-6` in `OPTIONS`).
- `bind_checkconf` runs `named-checkconf` on the main config `onchanges` of the
  config files and is `require_in` the `bind` service: a broken config blocks
  the reload. Its `onchanges` list mirrors the conditional file states — add a
  new config file to both. Zone files are not checked.

### Zones

The loop at the bottom of `config.sls` iterates views, with the key `False`
standing for the top-level `bind:` pillar so non-view zones go through the same
code. For each `configured_zones` entry:

- File name: `configured_zones:<zone>:file` (the zone name then becomes the
  file name minus `.txt`), else `available_zones:<zone>:file`. Records are
  always read from the global `bind:available_zones`, even inside a view.
- Content: if `available_zones:<zone>:records` exists, the file is generated by
  `files/zone.jinja`; otherwise it is copied from `salt://zones/<file>`
  (`zones_source_dir`, outside this formula). No `available_zones` entry at all
  = externally managed file, nothing written.
- Only `type: master` zones with `managed` unset or true get a file.
- `soa:serial: auto` switches to a two-file layout: records go to
  `<file>.include`; a `module.wait` on `dnsutil.serial` fires when it changes;
  `<file>` holds only the SOA (serial from `dnsutil.serial`) and an `$INCLUDE`.
- `generate_reverse` (`reverse_zone.jinja`) fills the zone's `PTR` records from
  the `A` records of `for_zones` (or every zone with `any`) that fall in `net`.
- `dnssec: true` runs `zonesigner` (dnssec-tools) via `prereq`;
  `auto-dnssec` generates ZSK/KSK with `dnssec-keygen` in the key directory.

## Tests

- InSpec controls branch on `os[:name]`, not on the shared `system` resource.
  Most of their per-OS branches cover platforms `kitchen.yml` no longer has.
- `config_spec.rb` matches `named.conf.local` with whitespace-exact multi-line
  regexes: any whitespace change in `named.conf.local.jinja` breaks them.
- `zones_spec.rb` checks the generated zone files, including the
  `serial: auto` pair and the generated `PTR` records.
- `service_spec.rb` checks the `bind9` unit (`map.service` on Debian, an alias
  of `named.service`).
- `_mapdata` runs, but there are no reference dumps under
  `test/integration/default/files/` to compare it to.
